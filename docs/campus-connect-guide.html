Overview

Campus Connect is a real, database-backed Django e-commerce platform — a customer storefront plus a complete staff back office. Nothing here is a mockup: products, payment methods, prices, pickup points and store info all live in the database and are editable by staff.

🛒 Storefront

Browse products, add to cart, check out, upload payment proof, and track orders.

🧾 Order workflow

Numbered CC-000001 orders with a full status lifecycle and audit history.

🔐 Human payment check

A staff member must verify an uploaded proof — orders are never auto-marked paid.

📦 Inventory

Stock is committed on payment confirmation; selling out flips products to Out of Stock.

👥 RBAC

Five staff roles with permissions enforced server-side, not just hidden in the UI.

⚖️ Regulated items

Age-restricted products stay un-buyable until a compliance record is approved.

Run it locally

You need Python 3.12+ and the files from the delivered zip. By default it runs on zero-config SQLite — no database server needed.

unzip campus-connect-ecommerce.zip
cd savana
pip install -r requirements.txt
python manage.py migrate

# create the first admin + seed a demo catalogue
export SAVANA_ADMIN_USER=admin
export SAVANA_ADMIN_EMAIL=you@example.com
export SAVANA_ADMIN_PASSWORD='choose-a-strong-password'
python manage.py savana_setup --demo

python manage.py runserver

Then open the pages below in a browser:

Storefront

http://127.0.0.1:8000/

Staff back office

http://127.0.0.1:8000/backoffice/

Django admin

http://127.0.0.1:8000/admin/

The folder is named savana and the setup command is savana_setup — these are internal names only. Everything a customer sees reads “Campus Connect”.

Use Supabase hosted Postgres

To store data in Supabase instead of SQLite, give the app one connection string. The database is resolved in this order: SAVANA_DATABASE_URL (or DATABASE_URL) → discrete SAVANA_POSTGRES_* vars → SQLite.

1. Get the connection string

In Supabase: Project Settings → Database → Connection string → URI. Use the connection pooler host (port 6543) for most deployments, or the direct host (port 5432).

2. Point the app at it

export SAVANA_DATABASE_URL='postgresql://postgres.<ref>:<password>@aws-0-<region>.pooler.supabase.com:6543/postgres'
pip install -r requirements.txt      # installs the psycopg driver
python manage.py migrate
python manage.py savana_setup --demo
SSL is required by Supabase and turned on automatically (sslmode=require). Override with SAVANA_DB_SSLMODE if needed. Special characters in the password can be percent-encoded in the URL — they are decoded correctly.

Customer journey

The path a shopper takes from browsing to a completed order.

Browse shop→ Add to cart→ Checkout→ Get CC- number + pay instructions→ Upload payment proof→ Wait for staff verification→ Order confirmed & fulfilled

Checkout validates stock (you cannot over-order), creates an order with a unique CC-000001 style number, and shows the payment methods and instructions pulled from the database. The customer uploads proof, then a human on staff must verify it before anything is marked paid.

Order lifecycle

Every order moves through these statuses. Each change is recorded with who did it and when.

Submitted→ Payment Pending→ Payment Proof Uploaded→ Payment Verification→ Payment Confirmed→ Processing→ Ready for Fulfilment→ Fulfilled

Branch / exception states

Cancelled Rejected Payment Failed Out of Stock
Stock is committed when a verifier confirms payment, so inventory only drops for genuinely paid orders. If a product's stock hits zero it automatically flips to Out of Stock, and restocking flips it back to Published.

Back office

Where staff run the store. Every action is permission-checked on the server and written to the audit log.

Dashboard

Live operational snapshot of orders needing attention.

Order queue & detail

Open an order, see its proof and history, and take the next action.

Verify / reject payment

Only a Payment Verifier can confirm or reject — rejection records a reason.

Advance fulfilment

Move confirmed orders through Processing → Ready → Fulfilled.

Inventory

View stock and make adjustments; movements are tracked.

Audit log

Who did what, when — e.g. payment rejections are logged.

Roles & access

Five staff roles seeded at setup. Permissions are attached to Django groups and enforced server-side.

RoleCan do
Super AdminFull access to everything.
Store AdminProducts, inventory, orders and customers.
Payment VerifierPayment info plus the verify_payment / reject_payment actions.
Fulfilment StaffOrder processing only (update_fulfilment) — cannot verify payments.
Content ManagerProducts & storefront content, no financial admin.

Security rules

No auto-paid orders. Uploading a screenshot never marks an order paid — a human verifier must explicitly confirm it.
RBAC is server-side. Permissions are enforced in the backend, not merely hidden in the UI, so a hidden button can't be bypassed by crafting a request.
Private payment proofs. Proof files are stored outside the public media path; anonymous requests get a 403, and only authorised staff can open them.
Nothing sensitive is hard-coded. Account numbers, payment instructions, pickup locations and store info live in the database; secrets and admin credentials come from environment variables.
Regulated products are gated. Age-restricted items can't be transacted until an approved compliance record exists.
